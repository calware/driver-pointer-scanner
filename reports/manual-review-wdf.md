# KMDF candidate review (offline)

The preliminary KMDF flow produced 11 image-level leads. I inspected the reported callsites in installed PE images without loading drivers, opening device handles, or sending IOCTLs. The corrected analyzer retains only `bxvbda.sys` as a register-argument candidate; the other ten are stack-only input-provenance leads. None establishes a feasible user IOCTL that passes request input as a meaningful argument through a writable callback.

| Image | Callsite observation | Review outcome |
|---|---|---|
| `bxvbda.sys` | At `0x18d9` the code loads `.data` slot `0x7e3d8`, sets `ECX=0xffff`, then calls RAX; at `0x18eb` it loads `0x7e3e0`, clears ECX, then calls RAX. At `0x1984`, slot `0x7e3e8` is a nullable tail-call wrapper whose fallback reads `[RCX+2]`. The analyzer's request-input taint is in R8, which these small wrappers do not set or establish as a formal parameter. WDF input retrieval at a separate callback path is detected, but the joined provenance does not establish a valid route to these wrappers. | Register-argument **candidate unconfirmed**; likely carried-register taint. Slot initialization and a feasible request path still need proof. |
| `monitor.sys` | `0x4fcc` calls helper `0x6480` after setting local context and testing a nullable slot; the reported input occurs only in seventh stack location. `0x506f` sets RCX/RDX/R8 from helper context before calling the same helper. | Stack-only lead; formal buffer parameter unproved. |
| `PktMon.sys`, `RzCommon.sys`, `scfilter.sys`, `UcmCx.sys`, `UcmUcsiAcpiClient.sys`, `WifiCx.sys` | Cited callsites `0x27fa`, `0x1c56`, `0x4c44`, `0x5a36`, `0x1227`, and `0x1679e` build tracing arguments with `EDX=0x2b` and other trace descriptors. The scanner's input label is on a seventh stack location, not a demonstrated callback buffer argument. | Stack-only tracing leads; no confirmed requested pattern. |
| `vmbusr.sys` | At `0x14813`, `R10D=0x11` and `LEA EDX,[R10+0x1a]` form trace code `0x2b`; surrounding writes build trace descriptors. The claimed input labels are fifth/seventh stack locations. | Stack-only tracing lead; no confirmed requested pattern. |
| `vpci.sys` | At `0x1cb0` and `0x1e26`, `EDX=0x2b` and several stack values are explicitly prepared for the trace call; the reported fifth-argument input association is not established by this setup. | Stack-only tracing lead; no confirmed requested pattern. |
| `winverbs.sys` | At `0xbe25`, `RCX` comes from `[RBX+0x20]`, R8/R9 are cleared, and the fifth stack value is a local pointer; the actual call operand is `[RIP+0x22e5]`. At `0xb713`, the actual call operand is `[RIP+0x29f7]`, while the reported writable slot is a separate earlier RAX source. | Slot-to-call association and formal input argument unproved. |

These observations reject the scanner's reported witnesses as confirmation. They do not prove absence of all possible behavior in any driver. The static model still lacks concrete runtime object state, IOCTL success predicates, and a safe observation of user-mode handle accessibility. `reports/wdf-callsite-review.txt` records the callsite disassembly excerpts used here.
