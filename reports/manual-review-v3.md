# V3 installed-driver candidate review (offline)

This review covers all 22 scanner candidate images in `reports/installed.json`. It is based on the installed PE files, without opening devices, issuing IOCTLs, loading drivers, or modifying driver files. The scanner uses a fixed-point **MAY** analysis and explicitly does not preserve correlated branch predicates. None of these findings confirms a valid user IOCTL that passes `Irp->AssociatedIrp.SystemBuffer` as a meaningful formal argument through a writable callback slot. A rejected **reported witness** is not proof that the whole driver lacks every possible callback pattern; access control and runtime registration remain untested.

On Windows x64, the first four integer/pointer arguments are RCX, RDX, R8, and R9. The fifth is at `[rsp+0x20]` immediately before a call, the sixth at `[rsp+0x28]`, the seventh at `[rsp+0x30]`, and the eighth at `[rsp+0x38]`. Values left in these registers/stack locations by unrelated code are not evidence that the target accepts them as data parameters. For CFG dispatch, the destination in the cited `jmp/call [rip+disp]` is the PE load-config `GuardCFDispatchFunctionPointer`; it leads to a `jmp rax` stub. The writable `.data` slot, when relevant, is an earlier source for RAX.

The presence of a writable slot could matter under a **separate, hypothetical prior pointer corruption**. This review found no such writer controlled by an unprivileged caller and made no vulnerability claim. The clearest scanner defects are conflating the CFG dispatch pointer with a data-slot callback, carrying `SystemBuffer` MAY taint into unrelated tracing/error paths, and labeling unused stack locations as formal arguments. `netbt.sys` and `vsock.sys` retain genuinely unresolved target initialization; several other zero-initialized slots also need any runtime writer and feasible request path established before a stronger claim.
